<objective>
Fix the Google web sign-in blocker on the deployed PWA (https://my-project-joost.web.app): `signInWithIdToken` currently fails with a 400 nonce-mismatch because `account_section.dart` never sends a `nonce:` to Supabase while the Google ID token *does* carry a `nonce` claim (Bug 1, O3M-01, the blocker). Also stop the guaranteed-to-fail `authorizeScopes()` popup that the web `authenticationEvents` listener triggers outside the user-gesture call stack, which spams the console with "Failed to open popup window" on every sign-in (Bug 2, O3M-02, noise — already non-fatal, but worth silencing since it can never succeed on web).

The fix is a single nonce, generated once per app run in `CalendarService` (the one place `GoogleSignIn.instance.initialize()` may be called, per AUTH-05), fed as the SHA-256-hashed value into Google's `initialize(nonce:)` and as the raw value into Supabase's `signInWithIdToken(nonce:)`. This covers both the Android and web sign-in branches, since both already funnel through `_handleSignInSuccess()`.

Purpose: Unblock Google sign-in on web — the only currently-broken platform (Android sign-in has not yet been verified end-to-end and is intentionally left untouched beyond gaining the shared nonce, per Phase 19 plan 19-07).
Output: `CalendarService` exposes a stable per-run nonce; `account_section.dart` passes it to Supabase and stops the doomed web popup attempt; `crypto` promoted from transitive to direct dependency; unit tests for the new hashing logic.
</objective>

| Browser/app <-> Supabase Auth (`eu-west-3`) | Client sends `{idToken, accessToken, nonce}` to `signInWithIdToken`; Supabase verifies the JWT signature, audience, and now the nonce hash before issuing a session. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| O3M-T-01 | Spoofing / Replay | Google ID token <-> Supabase `signInWithIdToken` nonce handshake | mitigate | This plan *is* the mitigation: a CSPRNG-generated (`Random.secure()`) raw nonce is sent to Supabase, and its SHA-256 hash is embedded in the Google-issued ID token via `initialize(nonce:)` — restores the nonce-based binding between "this specific sign-in attempt" and "this specific ID token", closing the gap where `signInWithIdToken` was previously called with no nonce at all. |
| O3M-T-02 | Tampering | `CalendarService.hashNonce()` (SHA-256 computation) | accept | Pure client-side function operating on the client's own CSPRNG-generated value; standard OIDC nonce-hashing convention; no external/untrusted input reaches this function. |
