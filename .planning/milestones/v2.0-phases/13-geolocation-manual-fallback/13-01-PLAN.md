<objective>
Prove that Flutter's `geolocator_web` federated plugin already delivers real-coordinate forecasts transparently over HTTPS/localhost (LOC-06, no production code change needed per ARCHITECTURE.md), then close the two concrete gaps that stand between "the library works" and "the feature is safe and usable on web": (1) `GpsPermissionNotifier.openSettings()` currently calls `permission_handler`'s `openAppSettings()` unconditionally, which throws `UnsupportedError` on web -- and because `geolocator_web`'s `requestPermission()` maps *every* denial or timeout to `LocationPermission.deniedForever` (confirmed by reading `geolocator_web`'s source directly), this is not a rare edge case on web, it is the common path; (2) the existing manual city picker in `ProfileScreen` is a plain list row today, not the prominent "primary path" LOC-07 requires when geolocation is denied/times out on web.

**Framing note (MVP_MODE):** ROADMAP.md's Phase 13 `**Goal:**` line is written as a technical/UX outcome ("Web users get their forecast for their real location... with the manual city picker promoted to an equally prominent, load-bearing path"), not in strict `As a / I want to / so that` format -- consistent with every other v2.0 phase goal in this ROADMAP (see Phase 11/12 precedent) and with the orchestrator's explicit MVP_MODE instruction for this phase. Reframed for reference: **As a** web user whose browser denies or fails to grant location access, **I want to** immediately see a clear, tappable way to pick my city, **so that** I still get an accurate ride-window forecast without getting stuck on a screen that silently failed to locate me. Per the orchestrator's instruction, vertical-slice ordering is applied here as: guard the unsafe call first (so nothing can crash), then ship the promoted UI in the same plan (so the "surfaced immediately" behavior is real), then manually prove the whole grant/deny loop in a real browser -- not split across horizontal layers/plans.

**Scoping note on production/iPhone verification (mirrors Phase 12's precedent):** Firebase Hosting does not exist until Phase 17. Geolocation requires a secure context (HTTPS), but Chrome and Safari both treat `localhost` as a secure-context exception, so `flutter run -d chrome` on localhost CAN exercise the real browser Geolocation permission prompt and API today. This plan's manual verification (Task 3) covers what's verifiable now: desktop Chrome on localhost granting permission -> real-coordinate forecast, and denying/timing out -> prominent city picker. The "real iPhone in Safari on the deployed HTTPS domain" portion of ROADMAP success criterion 1 is explicitly deferred to Phase 17 (or a dedicated Phase 16 iOS device pass) and is NOT silently dropped -- it is called out again in `<verification>` below.

Output: A testable `isWebPlatform` seam, a guarded `GpsPermissionNotifier.openSettings()`, a promoted web city-picker CTA in `ProfileScreen`, new widget/unit tests proving both, and a manually-verified real-browser grant/deny/timeout pass.

GeolocatorPlugin.requestPermission() on web: calls `_geolocation.getCurrentPosition()` internally inside a try/catch. On success it returns `LocationPermission.whileInUse`. On ANY failure (user denies the browser prompt, or the request times out, or any other error) it returns `LocationPermission.deniedForever` -- never plain `denied`. `denied` only ever comes from `checkPermission()` reading the browser's `navigator.permissions.query({name:'geolocation'})` result of `'prompt'` (before the user has been asked this session). This is why the deniedForever path -- not the denied path -- is where LOC-07's "primary path" promotion matters most on web.

GeolocatorPlugin's web implementation: `getLastKnownPosition()`, `openAppSettings()`, `openLocationSettings()`, `getServiceStatusStream()` each `throw UnsupportedError(...)`. Confirmed via grep that `getLastKnownPosition` has zero call sites anywhere in `lib/` -- only `openAppSettings` is actually called, from `GpsPermissionNotifier.openSettings()`.

Current `lib/providers/gps_permission_notifier.dart` (full file, 27 lines): imports `geolocator`, `permission_handler`, `riverpod_annotation`; `@riverpod class GpsPermissionNotifier extends _$GpsPermissionNotifier` with `build()` returning `Geolocator.checkPermission()`, `requestPermission()` calling `Geolocator.requestPermission()` and setting `state = AsyncData(result)`, and `openSettings()` whose entire body is `await openAppSettings();`.

Current `lib/features/profile/profile_screen.dart` LOCATIE section (lines 242-302), three conditional elements inside the `ListView`'s `children:` list, in this order:
1. `if (permission == LocationPermission.deniedForever)` -> a `Card` (color `Theme.of(context).colorScheme.errorContainer`) containing `Text(s.locationBlocked)` (bold titleSmall), `Text(s.locationBlockedHint)`, and a `TextButton(onPressed: () => ref.read(gpsPermissionProvider.notifier).openSettings(), child: Text(s.openSettings))`.
