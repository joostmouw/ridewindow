<objective>
Wire Drift's web backend (`DriftWebOptions` + `sqlite3.wasm` + `drift_worker.dart.js`) into the existing `AppDatabase._openConnection()` so the same Drift schema that already works natively on Android also persists data in the browser across a full page reload — and prove it with a real, manual browser test rather than a successful build alone.

**Framing note (MVP_MODE):** ROADMAP.md's `**Goal:**` line for Phase 12 is written as a technical/infrastructure outcome ("User data ... reliably persists in the browser across page reloads, on the same Drift schema used natively"), not in strict `As a / I want to / so that` user-story format — this is a data-layer enabler phase, not a new user-facing feature, and none of the other v2.0 ROADMAP phase goals use that format either. Per the orchestrator's explicit instruction for this phase, vertical-slice task ordering is applied (config + wiring + manual proof stay in one plan, not split into horizontal layers) rather than blocking on a formal `/gsd mvp-phase 12` user-story conversion. Reframed for reference: **As a** RideWindow web user, **I want to** have my cached weather data survive a page reload without a fresh network fetch, **so that** the app feels instant on repeat visits and I don't silently lose state every time I revisit the browser tab.

**Correction to the ROADMAP's illustrative example:** ROADMAP.md's success criterion 2 uses "toggle an availability cell" as an example write. Per STATE.md's Phase 3 decision (03-03) and confirmed by reading `lib/providers/availability_notifier.dart`, availability-grid writes go through `SharedPreferences` (`shared_preferences_web`, already fully cross-platform, zero Phase 12 changes needed) — NOT through Drift's `AvailabilityGridEntries` table. The only data that actually round-trips through `AppDatabase`/Drift today is the weather forecast cache (`ForecastCacheEntries` + `HourlyForecastEntries`, written via `ForecastDao.replaceAll()` inside `WeatherRepository.getForecast()`, on a 1-hour cache TTL). This plan's manual verification therefore proves persistence using the weather-cache write path — the actual Drift-backed data flow in this codebase — which is a stronger and more accurate proof of PERS-06 than the availability-grid example.

Purpose: Phase 11 proved the web build renders and navigates; Phase 12 is the highest silent-failure-risk step in the whole v2.0 milestone per ARCHITECTURE.md and PITFALLS.md — a `flutter build web` can succeed with zero errors while Drift silently falls back to in-memory storage or throws only at runtime.
Output: `AppDatabase` opens on web via `DriftWebOptions`, version-matched `sqlite3.wasm`/`drift_worker.dart.js` assets committed to `web/`, and a manually-verified write-then-reload persistence proof.
</objective>

```dart
static const Duration _cacheDuration = Duration(hours: 1);

Future<List<HourlyForecast>> getForecast({double lat = kDefaultLat, double lon = kDefaultLon}) async {
  final cache = await _db.forecastDao.latestCache(lat: lat, lon: lon);
  if (cache != null && DateTime.now().difference(cache.fetchedAt) < _cacheDuration) {
    return _db.forecastDao.hourlyForecasts(cacheId: cache.id);
  }
  final fresh = await _client.fetch(lat, lon); // OpenMeteoClient -> https://api.open-meteo.com/v1/forecast
  await _db.forecastDao.replaceAll(lat: lat, lon: lon, forecasts: fresh);
  ...
  return fresh;
}
```
Within the 1-hour cache window, a second call reads exclusively from `_db.forecastDao` (Drift) with zero network request — this is the exact mechanism the manual verification task exploits to prove Drift-web persistence.
