<objective>
Wire the web-only foreground refresh trigger that replaces WorkManager (REFRESH-01), make the existing "Last updated" label and pull-to-refresh gesture (REFRESH-02/03, both already partially built pre-phase) reflect reality at all times, and stop `SlotsNotifier`/`HomeScreen` from wiping the screen blank when a refresh fails after previously succeeding (REFRESH-04).

**Framing note (MVP_MODE):** ROADMAP.md's Phase 14 `**Goal:**` line is written as a technical/UX outcome ("Web users see fresh (or clearly-labeled stale) weather data without any background task, driven entirely by page load, regained focus, and manual pull-to-refresh"), not in strict `As a / I want to / so that` format -- consistent with every other v2.0 phase goal in this ROADMAP (Phases 11-13 precedent, all planned the same way). Reframed for reference: **As a** web user who checks RideWindow once or twice a week, **I want to** always see how fresh the forecast is and never hit a blank screen when my connection or a fetch briefly fails, **so that** I can trust the ride windows I'm looking at without needing to think about whether the app "refreshed in the background" the way the Android version did. Per the orchestrator's instruction, this plan is one vertical slice, not split into horizontal layers: Task 1 wires the trigger + the always-visible freshness signal, Task 2 makes failure states resilient instead of blank, Task 3 proves both in a real browser.

**Pre-existing-code audit (done during planning, do not re-discover this):**
- `lib/providers/last_refreshed_provider.dart` already exists (`lastRefreshedProvider`, reads `weather.lastRefreshed` from `SharedPreferences`). It is NOT wired to `weatherProvider` reactively today -- it only re-reads on `_HomeScreenState.didChangeAppLifecycleState`'s `resumed` branch, or on its own initial `build()`. This plan adds the missing reactive link (Task 1).
- `HomeScreen` already has a `RefreshIndicator` wrapping the `CustomScrollView`, with `onRefresh: () => ref.refresh(weatherProvider.future)` -- REFRESH-02's core mechanism is DONE. This plan does not rebuild it, only confirms it keeps working and that a refresh also updates the last-updated label (Task 1's listener covers this automatically).
- `HomeScreen._HomeScreenState` already `with WidgetsBindingObserver` and already overrides `didChangeAppLifecycleState`, calling `ref.read(lastRefreshedProvider.notifier).refresh()` on `resumed` (built in an earlier native-background-refresh phase). This plan adds one line to that existing branch -- it does NOT introduce a new observer or provider.
- `WeatherRepository.getForecast()` (`lib/data/repositories/weather_repository.dart`) already implements cache-then-network with a 1-hour TTL and already writes the `weather.lastRefreshed` SharedPreferences key on every real network fetch (not on cache hits). This plan does not touch this file -- `ref.invalidate(weatherProvider)` re-runs `WeatherNotifier.build()`, which calls back into this same repository, so the existing TTL logic still governs whether an actual HTTP request happens.
- The current subtitle logic in `HomeScreen.build()` only shows the "Bijgewerkt/Updated" label when there are zero ride slots (`slotCount == 0`) -- it is REPLACED, not hidden entirely, when `slotCount > 0`. This is the concrete gap behind REFRESH-03's "at all times" wording and is fixed in Task 1.
- `SlotsNotifier.build()` (`lib/providers/slots_notifier.dart`) currently treats `weatherValue.hasError` as equivalent to "no data" and returns `const SlotsLoaded([])` unconditionally on any weather error -- even when Riverpod has preserved the previous successful value (`AsyncValue.hasValue` stays `true` through an error that follows a success, this is Riverpod's built-in "keep previous data" behavior for refresh-triggered errors, not something this plan needs to build). This is the concrete root cause of REFRESH-04's "blank screen" risk and is fixed in Task 2, not just papered over in the UI layer.

Purpose: Replace the WorkManager-shaped mental model of "the app refreshes itself" with a foreground-driven one that is honest about freshness and resilient to failure, without touching `WeatherNotifier`'s or `SlotsNotifier`'s core computation logic more than the one necessary guard.
Output: A web-gated resume-refresh trigger, an always-current "Last updated" label, a stale-data banner + preserved slots on fetch failure, matching widget/unit tests, and a manually-verified real-browser pass.
</objective>
