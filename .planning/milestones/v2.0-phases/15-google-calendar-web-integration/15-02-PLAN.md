<objective>
Obtain the real, deployed HTTPS Firebase Hosting domain that CAL-07 explicitly requires ("not just localhost"), and manually verify the full "Add to calendar" flow built in Plan 15-01 end-to-end against that real production URL -- in a desktop browser, and mandatorily on a real iPhone in Safari.

**Framing note (MVP_MODE):** Continuing the same user story as 15-01 (**As a** web user who found a good ride window, **I want to** tap one button and have it land on my real Google Calendar, **so that** I actually book the ride) -- this plan is the second vertical slice: it extends the already-working localhost flow to the real environment a real iPhone user will actually be in. It is a genuine, separate requirement (CAL-07) with its own ROADMAP success criteria, not "polish" tacked onto 15-01; it depends on 15-01's code being in place first (dependency conflict, not a difficulty judgment) and could not run in Wave 1 because the Web OAuth client from 15-01 Task 1 must exist before a production origin can be registered against it.

**Pre-existing-gap audit (done during planning, do not re-discover this):**
- No `firebase.json`, `.firebaserc`, or Firebase project exists anywhere in this repo yet (confirmed via `find` at repo root). `DEPLOY-01`/`DEPLOY-02` (the hardened, final version of this same file) are formally Phase 17's job, which comes *after* Phase 15/16 in the ROADMAP -- RESEARCH.md Pitfall 5 flags this exact ordering gap and recommends a **lightweight, non-hardened** preliminary deploy inside this phase, which Phase 17 later extends rather than replaces.
- The Firebase CLI is not installed on this machine (`command -v firebase` returns nothing, confirmed during planning). `npm` and `node` ARE available (`/opt/homebrew/bin/npm`, `/opt/homebrew/bin/node`).
- Phase 12's SUMMARY (`.planning/phases/12-drift-web-persistence/12-01-SUMMARY.md`) explicitly left PERS-07 (the `sqlite3.wasm` Content-Type header) as an open carry-forward because no Firebase Hosting deployment existed at the time: "the authoritative Content-Type verification happens in Phase 17 against the real Firebase Hosting deployment." Since this plan creates the first-ever deployment, Task 2 proactively adds the wasm header rule to `firebase.json` now (cheap, and required for the app to even boot correctly on the deployed domain, which this plan's own verification depends on) -- but PERS-07 sign-off itself remains formally Phase 17's to confirm, per that SUMMARY's explicit scoping. This plan does not claim PERS-07 credit.
- The Google Cloud project reused here is the SAME one from 15-01 Task 1 (which itself reuses Phase 9's Android OAuth project) -- Firebase Hosting is added onto an existing GCP project via `firebase projects:addfirebase`, not a brand-new project, so the Web OAuth client's origin allowlist stays a single-client, single-project story (RESEARCH.md Open Question 3 default).

```
{
  "hosting": {
    "public": "build/web",
    "ignore": ["firebase.json", "**/.*", "**/node_modules/**"],
    "rewrites": [
      { "source": "**", "destination": "/index.html" }

  }
```
