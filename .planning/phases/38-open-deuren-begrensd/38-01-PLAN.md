**Kop (commentaar).** Aanleiding: epic 75 (Dicht huis), fase 38, RATE-01 t/m RATE-03, na de nulmeting van 37-NULMETING.md. Verantwoording volgens de CLAUDE.md-regel: dit is server-functie nummer 15 (`enforce_insert_rate_limit`); de client kan dit aantoonbaar niet, want de grens moet ook gelden voor builds die al in het veld staan (RATE-04) en voor een aanvaller die met de publieke sleutel schrijft. Vermeld dat CLAUDE.md/AGENTS.md pas in fase 40 (AFR-02) het aantal bijwerken. Sectie over de plafonds met de metingen uit de nulmeting: feedback max per account op een dag 3 -> 30; drukste toestel anoniem ~2 -> 20 per toestel; app_events drukste toestel op een dag 12 -> 120 per toestel en per afzender. Sectie afzender: md5(dag + ip), hooguit één dag bewaard (fase 40, AFR-01, beschrijft het in het privacybeleid), en waarom de afzender apart telt: roteren met device_id's mag niet helpen. Sectie terugdateren: de teller loopt op de serverklok, een meegestuurde created_at verplaatst geen quota (de deur die 0014 opmerkte gaat hier dicht). Sectie wat dit níet is: geen captcha, geen App Check (pas als de metingen erom vragen), app_events krijgt geen nieuwe lengtechecks want 0008 begrenst die tabel al, en de anonieme feedbackroute blijft open (FB-03).

**SQL, binnen `begin; ... commit;`:**

1. `alter table public.feedback add column device_id uuid;` plus `comment on column` (doel: dagplafond per toestel; aangemaakt door de app bij het eerste feedbackbericht; builds vóór deze fase sturen hem niet en vallen onder de afzendertelling). Geen FK, geen not null.

2. CHECKs op feedback, alle drie met een naam die de reden draagt:
   `comment is null or char_length(comment) <= 2000`;
   `context is null or char_length(context::text) <= 8000`;
   `rating is null or rating between 1 and 5`.

3. `create table public.rate_limit_counts (kind text not null, day date not null, subject text not null, n bigint not null default 0, primary key (kind, day, subject));` met comment, `enable row level security`, géén policies, géén grants (expliciet vermelden in commentaar: na 0006 erft een nieuwe tabel geen clientrechten; de trigger schrijft als eigenaar).

4. Eén trigger-functie:
   `create function public.enforce_insert_rate_limit() returns trigger language plpgsql security definer set search_path = ''` met eerste body-regel `#variable_conflict use_column`. Gedrag:
   - `l_kind := tg_table_name;` `l_today := (now() at time zone 'Europe/Amsterdam')::date;`
   - Opruimen: `delete from public.rate_limit_counts where kind = l_kind and day < l_today;` (zo is de afzenderhash hooguit één dag bewaard, zonder cron).
   - Header lezen, robuust tegen alle drie de toestanden (afwezig, lege string, ongeldig JSON): alleen casten als de GUC niet-leeg is; `x-forwarded-for` splitsen op de eerste komma, trimmen; `l_sender := 'sender:' || md5(l_today::text || ':' || ip)`. Bij null: géén afzenderonderwerp (SQL Editor en pooler blijven werken).
   - Onderwerpen en plafonds als paren, per tabel:
     feedback: sender|20; als `new.user_id is not null` dan `account:<uid>`|30; als `new.device_id is not null` dan `device:<uid>`|20.
     app_events: sender|120; `device:<uuid>`|120 (kolom is not null).
   - Per onderwerp: `insert into public.rate_limit_counts (kind, day, subject, n) values (l_kind, l_today, l_subject, 1) on conflict (kind, day, subject) do update set n = public.rate_limit_counts.n + 1 returning n into l_n;` en als `l_n > plafond`: `raise exception 'rw_rate_limited:%:%', l_kind, l_soort;`. Door de transactie van de insert rolt alles terug, ook de tellerverhogingen die al waren gelukt: geen halve telling.
   - `return new;`

5. Triggers aan beide tabellen: `create trigger rate_limit before insert on public.feedback for each row execute function public.enforce_insert_rate_limit();` en hetzelfde voor `public.app_events`.

6. `revoke all on function public.enforce_insert_rate_limit() from public, anon, authenticated;` (les uit 0015) en géén grant aan wie dan ook: alleen de eigenaar, via de triggers.

**Controle-sectie onderaan (commentaar)**, zoals 0009/0014: query op `information_schema.role_table_grants` voor rate_limit_counts (verwacht: alleen postgres), `has_function_privilege('anon', 'public.enforce_insert_rate_limit()', 'execute')` (verwacht false), en een probeer-insert met een comment van 2001 tekens (verwacht: geweigerd door de CHECK).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon/authenticated (publieke sleutel) → INSERT feedback/app_events | de grens moet in de database liggen, want builds in het veld krijgen geen update (RATE-04) |
| security definer-trigger → rate_limit_counts | de functie schrijft een tabel waar de aanroeper geen recht op heeft; uitvoer is een interne teller, nooit leesbaar voor de client |
| request.headers (GUC) → afzenderhash | onbetrouwbare invoer: alleen lezen, trimmen, hashen; een lege of ongeldige GUC mag de insert nooit breken |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-38-01 | Elevation of privilege | trigger-functie, PUBLIC-execute | mitigate | revoke van public/anon/authenticated; testcheck 1 |
| T-38-02 | Tampering | client-gezette created_at | mitigate | teller op de serverklok; testcheck 8 |
| T-38-03 | Spoofing | roterende device_id's | mitigate | afzender telt apart; testcheck 6 |
| T-38-04 | DoS | massale inserts | mitigate | per-toestel én per-afzender plafonds; weigering is goedkoop (één tellerrij) |
