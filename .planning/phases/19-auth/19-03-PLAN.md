<interfaces>
**google_sign_in 7.2.0 API surface, verified live against pub.dev (2026-07-26) — do not use 6.x-shaped snippets from Supabase's own docs (PITFALLS.md #1):**

- `GoogleSignInAccount` has `.email` (String), `.id` (String), `.displayName` (String?), `.photoUrl` (String?), `.authentication` (→ `GoogleSignInAuthentication`, which has **only** `.idToken`, no access token), `.authorizationClient` (→ `GoogleSignInAuthorizationClient`).
- `GoogleSignInAuthorizationClient.authorizationForScopes(scopes)` returns `GoogleSignInClientAuthorization?` **without prompting** — null if not yet authorized. `.authorizeScopes(scopes)` does the same but may prompt. Both `GoogleSignInClientAuthorization` instances expose `.accessToken` (String).
- `GoogleSignIn.instance.authenticate({List<String>? scopeHint})` → `Future<GoogleSignInAccount>` — interactive, throws `GoogleSignInException` (check `.code == GoogleSignInExceptionCode.canceled` for user cancellation) on Android; **throws unconditionally on web**.
- `GoogleSignIn.instance.supportsAuthenticate()` → `bool` — the correct branch condition (D-06), not `kIsWeb`.
- `GoogleSignIn.instance.authenticationEvents` → `Stream<GoogleSignInAuthenticationEvent>` — the web-only path. Listen for `GoogleSignInAuthenticationEventSignIn`, which carries `.user` (a `GoogleSignInAccount`). Import `package:google_sign_in/web_only.dart` for `renderButton()` — this import is safe to use unconditionally on every platform (it is the federated-plugin facade, not a `dart:html`-gated file); only the *call* to `renderButton()` needs to stay inside the `!supportsAuthenticate()` branch.

**Supabase sign-in call (the 7.x-correct shape — Supabase's own docs show the removed 6.x `googleAuth.accessToken` API, ignore that part of their sample):**

`Supabase.instance.client.auth.signInWithIdToken(provider: OAuthProvider.google, idToken: <from account.authentication.idToken>, accessToken: <from authorizationClient>)`. Request only the `email` scope for the access token — not `calendar.events` — so plain sign-in never touches the Sensitive-scope 100-user cap (`docs/ACCOUNTS-OPERATIONS.md` §1).

**Test-environment graceful degradation (established pattern, see `test/features/profile_screen_calendar_test.dart`'s header comment):** any real call into `GoogleSignIn.instance` throws `MissingPluginException` in `flutter test` — there is no registered platform channel. Every entry point that calls into `GoogleSignIn.instance` (including `supportsAuthenticate()`, which this widget calls in `initState` to decide its platform branch) must be wrapped so a thrown exception degrades to a safe default (the Android/`ListTile` branch) rather than crashing the widget tree. This is what makes Task 3's widget tests possible without mocking the SDK.

**`_SectionHeader` cannot be imported.** It is a private class in `profile_screen.dart` (Dart privacy is per-file). Do not attempt to import or export it. Duplicate its exact style (a `Padding(EdgeInsets.fromLTRB(16,16,16,4))` wrapping a `Text` styled with `Theme.of(context).textTheme.labelMedium` in `colorScheme.primary`, bold) as a small private widget local to `account_section.dart` — this is a deliberate, small duplication chosen over refactoring 8 existing call sites in `profile_screen.dart` and widening this phase's diff on a file whose Calendar row is REG-04's gate.

Then create `lib/features/profile/account_section.dart` as a `ConsumerStatefulWidget` named `AccountSection`. Structure:

1. A private header widget duplicating `_SectionHeader`'s style (see `<interfaces>` — do not import the real one), rendering `S.of(context).sectionAccount`.
2. `build()` watches `ref.watch(authStateProvider)` and switches on its `AsyncValue<User?>`: `loading` → a `ListTile` with a small `CircularProgressIndicator` (strokeWidth 2, matching the existing Calendar row's loading affordance) and `accountLoading` text; `error` → treat identically to a `null` (signed-out) data value, never show a raw error to the user; `data: null` → the signed-out row; `data: user` → the signed-in row.
3. Signed-out row: in `initState`, determine the platform branch once via a try/catch around `GoogleSignIn.instance.supportsAuthenticate()`, defaulting to `true` (the Android/native branch) if the call throws — this is what keeps widget tests safe (see `<interfaces>`). If `true` (native): a `ListTile` in the app's existing style (leading `Icon(Icons.login)`, title `signInWithGoogle`, subtitle `accountSyncPromise`, `onTap` triggers the Android sign-in handler). If `false` (web): the same subtitle text above a `renderButton()` widget from `package:google_sign_in/web_only.dart`, with an `authenticationEvents` subscription set up in `initState` (only on this branch) reacting to `GoogleSignInAuthenticationEventSignIn`, cancelled in `dispose()`.
4. Android sign-in handler: guard against double-taps with a local `_busy` bool; call `CalendarService.ensureGoogleSignInReady()`, then `GoogleSignIn.instance.authenticate()`; on `GoogleSignInException` with `code == GoogleSignInExceptionCode.canceled`, do nothing (D-07, cancel is a choice not an error); on any other exception, show a `SnackBar` with `accountSignInError` and let the real exception reach the debug log (e.g. via `debugPrint`), never the SnackBar text; on success, call the shared completion step below.
5. Shared completion step (used by both the Android handler and the web `authenticationEvents` listener), taking a `GoogleSignInAccount`: read `.authentication.idToken` (guard null → treat as failure); resolve an access token via `authorizationClient.authorizationForScopes(['email'])`, falling back to `.authorizeScopes(['email'])` if that returns null; call `Supabase.instance.client.auth.signInWithIdToken(provider: OAuthProvider.google, idToken:, accessToken:)`; on success, if `ref.read(profileProvider).value?.userName` is null, call `ref.read(profileProvider.notifier).setUserName(account.displayName)` (D-04 — auto-fill only when empty, `setUserName` already exists on `ProfileNotifier` and already handles null/empty trimming). No success confirmation UI (D-07 — the section visibly changing is the proof).
6. Signed-in row: `ListTile` with leading a `CircleAvatar` built from `user.userMetadata?['avatar_url']` (a `NetworkImage`, wrapped so a load failure falls back to `Icon(Icons.account_circle)` rather than a broken-image glyph — use `CircleAvatar`'s `onBackgroundImageError` callback plus a boolean flag to switch to the fallback icon on error, since `CircleAvatar` does not automatically fall back), wrapped in `Semantics(label: s.accountAvatarSemanticLabel, ...)`; title showing the account's display name (from `user.userMetadata?['full_name']` or `user.userMetadata?['name']`, falling back to `user.email` if neither is present); subtitle showing `user.email`; trailing a `TextButton` labelled `accountSignOut` that opens the confirm dialog.
7. Sign-out confirm dialog: a standard `AlertDialog` (title `accountSignOutConfirmTitle`, body `accountSignOutConfirmBody`, a cancel action and a confirm action labelled `accountSignOut`). On confirm, call `Supabase.instance.client.auth.signOut()` only — do **not** call `CalendarService.disconnectCalendar()` or touch any local `SharedPreferences` key (D-12, D-03 of `19-CONTEXT.md`: sign-out ends only the Supabase session).
