<objective>
Do the console work. Everything in this plan is a manual action in a web UI that Claude cannot perform: Cloud Console, Play Console, and the Supabase dashboard. The value of writing it as a plan is that it becomes one short ordered checklist instead of steps scattered through three other plans, and that what was registered gets recorded rather than remembered.

One step in here has already cost this project a shipped, broken feature: registering **both** SHA-1 fingerprints, including the Play App Signing key. An app installed from the Play Store is signed with Google's key, not the local keystore, so registering only the local one produces a feature that works perfectly in testing and fails for every real user.

Output: credentials registered and verified, the DPA accepted, the policy confirmed live, the Data Safety form submitted, and `docs/CONSOLE-SETUP-CHECKLIST.md` recording all of it.
</objective>

**Getting the two SHA-1 fingerprints:**
- **Local release keystore:** `keytool -list -v -keystore <path> -alias <alias>` — the keystore path and alias are in `android/key.properties` or the signing config in `android/app/build.gradle.kts`. Claude can help construct this command; running it is local and safe.
- **Play App Signing key:** Play Console → your app → Release → Setup → **App integrity** → App signing key certificate. This one exists only in Play Console and cannot be derived locally. It is the one that gets forgotten.

**Why the web client ID goes into Supabase:** with the `signInWithIdToken` flow, the app obtains a Google ID token on the device and hands it to Supabase, whose auth server verifies the token's audience against the web client ID configured in its Google provider settings. Without it, sign-in fails server-side with an audience error that reads like a generic auth failure. See `.planning/research/PITFALLS.md` #3.

**Data Safety form.** This is a separate artifact from the privacy policy and it is easy to update one and forget the other. It must declare: account creation, collection of location and calendar-derived availability, server-side storage, data encrypted in transit, and a deletion route. Point the deletion URL at the anchor added to the privacy policy in plan 18-02.

**Scope fence:** no app code, no `pubspec.yaml`, no schema. The schema and RLS policies are Phase 21 — do not create tables now. Creating tables early without RLS is the exact hazard in `PITFALLS.md` #7.
