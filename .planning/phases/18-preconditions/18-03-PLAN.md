<objective>
Stop the free-tier Supabase project from pausing. A free project goes offline after 7 days without incoming API requests, and while it is paused nobody can sign in or sync until it is manually restored from the dashboard. With a handful of testers and irregular use, a quiet fortnight is entirely plausible — and the failure lands on the testers, not on the developer, so it may go unreported for days.

The mitigation is small: a scheduled job that makes one request every few days. The repository already exists (`joostmouw/ridewindow`) and has no workflows yet, so this is the first one.

Output: `.github/workflows/supabase-keep-warm.yml`, scheduled, hand-triggerable, and loud when it fails.
</objective>

<interfaces>
**Repository:** `https://github.com/joostmouw/ridewindow`. `.github/` does not exist yet — create it. This is the first workflow in the repo.

**Supabase project:** `https://hcdrydlgqpnmumfupgcx.supabase.co`, free tier, region `eu-west-3` (Paris).

**Endpoint choice.** The project's REST root (`/rest/v1/`) responds to an authenticated request without requiring any table to exist. This matters: the schema does not land until Phase 21, so a keep-warm job that queries a table would fail for the whole of Phases 18–20. The auth health endpoint (`/auth/v1/health`) is another table-independent option. Pick one that returns a 2xx on a healthy project and a non-2xx or connection failure on a paused one, and verify that behaviour rather than assuming it.

**Credentials.** Supabase's anon key is designed to be public — it ships inside the app bundle and the web JavaScript, and row-level security is what protects the data, not the key's secrecy. So storing it in a repository secret is tidiness rather than security. Use `secrets.SUPABASE_ANON_KEY` and `vars.SUPABASE_URL` anyway: it keeps the workflow readable, and it means rotating the key later is a settings change rather than a commit. The user must add both in repository settings — note this clearly in the summary, because the workflow will fail on its first run until they do.

**Interval.** The pause threshold is 7 days. Run every 3 days, so one missed or failed run still leaves margin. Do not run daily — it burns Actions minutes for no additional protection.

**Scope fence:** this workflow keeps a project awake. It does not build the Flutter app, run tests, deploy, or touch `pubspec.yaml`. The repository deliberately has no CI today, and this plan is not the place to introduce it — if CI is wanted it is its own decision.

**Known caveat to record, not solve:** GitHub disables scheduled workflows in repositories with no activity for 60 days. A repo under active development will not hit this, but if development genuinely stops, both the commits and the keep-warm job stop together — and then the project pauses. That is acceptable (a dormant project pausing is the correct outcome) but it should be written down rather than discovered.
</interfaces>

  <action>
Create `.github/workflows/supabase-keep-warm.yml`.

Triggers: a `schedule` cron running every 3 days, plus `workflow_dispatch` so the project can be woken by hand from the Actions tab without waiting.

The job runs on `ubuntu-latest` and makes a single authenticated HTTPS request to the Supabase project using `curl`, sending the anon key as both the `apikey` header and the `Authorization: Bearer` header (Supabase expects both). Use `--fail-with-body` (or check the status code explicitly) and `--max-time` so a hung connection cannot pin the runner.

Fail the job on any non-2xx response or connection failure. This is the part that carries the value: a job that swallows errors gives a green checkmark on a dead project, which is strictly worse than having no job at all — it removes the signal while leaving the problem. Echo the HTTP status into the job log so a failure is diagnosable from the Actions tab without re-running anything.

Read the URL from `vars.SUPABASE_URL` and the key from `secrets.SUPABASE_ANON_KEY`. Do not hardcode either. Add a guard step that fails with a clear message if either is empty, so the first-run failure says "you have not set the secret yet" rather than producing an opaque curl error.

Add a comment block at the top of the file explaining what it is for and why it exists — that free projects pause after 7 days, that this only prevents the pause and does not monitor health, and the 60-day repository-inactivity caveat. Someone finding this file in a year should not have to reconstruct the reasoning.

Name the workflow something self-explanatory in the Actions list, e.g. `Supabase keep-warm (free tier anti-pause)`.
