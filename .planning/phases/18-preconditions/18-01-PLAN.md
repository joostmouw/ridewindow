The two caps, stated correctly (this is the substance of PRE-07):
- **Auth/sign-in cap:** none in practice. Basic sign-in requests `openid`/`email`/`profile`, which are neither Sensitive nor Restricted and do not count toward any cap.
- **Calendar-connect cap:** 100 unique users, **lifetime**, cumulative — not concurrent, not resettable. It counts users who have ever granted the Sensitive `calendar.events` scope while the app is unverified.
- The trap: the cap follows **verification** status, not **publish** status. "In production" does not remove it. Only a full Google verification pass does, which this project deliberately does not pursue. `.planning/PROJECT.md` §Current State already states this correctly — reuse that wording rather than inventing new phrasing.
- There is no Google-side dashboard or alert for the counter, and building one is explicitly deferred (REQUIREMENTS.md "Future Requirements"). So the honest statement is that the number is currently unobserved.

Retention/export answer to record (PRE-09), per CONTEXT.md D-16/D-17/D-18:
- Deletion removes the user's rows immediately, via `on delete cascade` from `auth.users`.
- `feedback` rows survive deletion but are de-identified (`user_id` set to null via `on delete set null`). This is the one thing that outlives the account and must be stated plainly.
- Article 20 export is manual: query the three tables from the Supabase dashboard, export JSON, send within one month. The in-app export button is deferred.

PRE-08's real content on a free plan (CONTEXT.md D-05): there is no billing surface to alert on. What replaces it is (a) the keep-warm job from plan 18-03, (b) Supabase's pause-warning email reaching an address that is read, (c) a runbook line so "sync stopped working" is triaged in minutes.
