<objective>
Make the outbox drain actually run. Plan 21-10 gave `drain()` a caller, and that caller is
genuinely there — but it throws before doing any work, every single time, and the try/catch
swallows it. SYNC-05 is therefore still not delivered.

Found on a real device on 2026-08-04 (Oppo Find X9 Pro, app 1.0.15+16 — the build containing
21-10). The account row sat on "Syncing..." indefinitely. `adb logcat` after a
background/foreground cycle:

```
I/flutter: CloudSyncReconciler.reconcileOnForeground failed: Cannot use the Ref of
           cloudSyncReconcilerProvider after it has been disposed.
I/flutter: CloudSyncReconciler.drainOutbox failed: Cannot use the Ref of
           cloudSyncReconcilerProvider after it has been disposed.
```

Note that **both** methods fail. SYNC-04's foreground cloud read has been broken by the same
cause since plan 21-04 wired it; 21-10 only made the symptom visible by adding a second victim.
</objective>

<context>
**Root cause.** `cloudSyncReconciler` is declared with a bare `@riverpod` annotation, and
Riverpod 3 makes auto-dispose the default (see CLAUDE.md's Riverpod 3 notes — `AutoDisposeNotifier`
is now just `Notifier`). `CloudSyncReconciler` stores the `Ref` it was constructed with in a
field and uses it across `await` boundaries:

```dart
@riverpod
CloudSyncReconciler cloudSyncReconciler(Ref ref) => CloudSyncReconciler(ref);
```

Both call sites use `ref.read`, which establishes no listener:

- `lib/features/home/home_screen.dart:98` — `ref.read(cloudSyncReconcilerProvider).reconcileOnForeground();` (fire-and-forget)
- `lib/features/profile/account_section.dart:317` — `await ref.read(cloudSyncReconcilerProvider).drainOutbox();`

Nothing watches the provider, so it is disposed as soon as the read completes. The async body
then continues and touches `_ref` — `_ref.read(authStateProvider)`, `_ref.read(syncOutboxServiceProvider)`,
`_ref.read(profileRepositoryProvider.future)`, `_ref.invalidate(...)` — on a disposed Ref, which
throws. The existing try/catch converts that into a `debugPrint` and the UI shows nothing.

**Why the test suite is green — the same lesson as 21-10, one layer deeper.**
`test/providers/outbox_drain_wiring_test.dart` is a source-level structural scan: it asserts that
`SyncOutboxService` is constructed somewhere in `lib/` and that `drain()` has a caller outside its
defining file. Both remain true. The plan for 21-10 permitted that fallback when a behavioural
assertion would need heavy `SupabaseClient` mocking, and this defect walked straight through the
opening. 21-10's lesson was "assert the call site exists". This plan's lesson is
**"assert the call actually reaches its work"**. The unit tests of `drain()` itself pass because
they hold a `ProviderContainer` that stays alive for the whole test.

**Second, quieter bug in the same place.** Because `syncOutboxServiceProvider` is also bare
`@riverpod`, every `_ref.read(syncOutboxServiceProvider)` constructs a *fresh* `SyncOutboxService`.
The re-entrancy guard 21-10 added is an instance field, so two overlapping drains would each get
their own instance and the guard would never engage. Fixing only `cloudSyncReconcilerProvider`
would leave that intact.

**Why `drainOutbox()` cannot currently be tested without Supabase.** Its first statement is
`final client = Supabase.instance.client;`, which throws in tests
(`You must initialize the supabase instance before calling Supabase.instance` — visible eight
times in the current suite output, harmlessly caught). Moving that lookup inside the send closures
makes the method testable with an overridden fake service and costs nothing: the closures are only
invoked when there is a row to send, and on a real device Supabase is initialised long before any
drain.

**Scope boundary.** Do not redesign the reconciler, do not add connectivity listeners or retry
schedules (REQUIREMENTS.md "Out of Scope", restated in 21-10). This plan makes existing, already-tested
code actually execute.
</context>
