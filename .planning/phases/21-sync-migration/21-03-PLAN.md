<objective>
Build the offline outbox — the "one piece of genuinely new construction the stack switch forces" per `.planning/research/ARCHITECTURE.md` §4a. Supabase ships no offline write queue (unlike the Firestore plan this project moved away from), so SYNC-05 ("changes made while offline reach the cloud once a connection returns") needs a real, small, Drift-backed queue instead of an SDK feature.

This plan builds ONLY the queue and its drain mechanism — nothing here calls the actual Supabase HTTP API yet. `SyncOutboxService.drain()` is deliberately network-agnostic: it takes the *send* operation as an injected callback, not a `SupabaseClient`, so it is fully unit-testable without mocking Supabase's fluent query builder, and so this file never becomes a second place `background_task.dart`'s import graph could accidentally pick up a Supabase dependency through. Wave 3 (plans 21-04/21-05) is what actually wires repositories to enqueue into this outbox and wires the real Supabase calls into `drain()`'s callbacks.

Purpose: give every domain a single, small, already-battle-tested-in-spirit (mirrors this codebase's own `save(..., {stamp})` repository convention) place to say "this needs to reach the cloud eventually" without building a general sync engine — REQUIREMENTS.md's "Out of Scope" section explicitly rules out backoff schedules, connectivity listeners, and background draining; this plan does not build any of those.

Output: `SyncOutboxEntries` (new Drift table, schemaVersion 1→2), `SyncOutboxDao` (coalescing enqueue + drain-ready reads), `SyncOutboxService` (the drain loop itself), `lib/data/remote/supabase_tables.dart` (the table/RPC name constants every later plan in this phase references, so no file hand-types `'profiles'`/`'availability'`/`'planned_rides'`/`'migrate_account_data'`/`'delete_own_account'` as ad-hoc string literals).
</objective>

**`SyncOutboxEntries` table shape — exact columns:**

```dart
class SyncOutboxEntries extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get entity => text()();      // 'profile' | 'availability' | 'planned_ride'
  TextColumn get entityKey => text()();   // profile/availability: userId. planned_ride: '<userId>:<rideId>'
  TextColumn get operation => text().withDefault(const Constant('upsert'))(); // 'upsert' | 'delete'
  TextColumn get payload => text()();     // JSON-encoded row map for 'upsert'; '{}' for 'delete' (the filter is derived from entityKey)
  IntColumn get queuedAt => integer()();  // epoch-ms, matches the app's existing updatedAt convention
  IntColumn get attempts => integer().withDefault(const Constant(0))();
  TextColumn get lastError => text().nullable()();

  @override
  List<Set<Column>> get uniqueKeys => [
        {entity, entityKey},
      ];
}
```

The `uniqueKeys` constraint is what makes coalescing free: `SyncOutboxDao.enqueueOrCoalesce()` uses Drift's `insertOnConflictUpdate` (or `InsertMode.insertOrReplace` scoped to this unique index) so five toggles of the same setting produce one row whose `payload`/`operation`/`queuedAt` reflect only the latest state, with `attempts`/`lastError` reset to `0`/`null` on every fresh enqueue — a superseding write should always get a clean retry count, not inherit a previous failure's history.

**`SyncOutboxService.drain()` — network-agnostic signature, so this plan needs zero Supabase mocking:**

```dart
class SyncOutboxService {
  SyncOutboxService(this._dao);
  final SyncOutboxDao _dao;

  /// Drains every pending row. [upsertFn] and [deleteFn] are injected by the
  /// caller (Wave 3's AccountSyncService/repositories), which is where the
  /// real `SupabaseClient.from(table).upsert(row)` / `.delete()...` calls
  /// live — this class never imports package:supabase_flutter itself, which
  /// keeps it trivially unit-testable and keeps it out of any import graph
  /// REG-05 cares about.
  Future<void> drain({
    required Future<void> Function(String entity, String entityKey, Map<String, dynamic> payload) upsertFn,
    required Future<void> Function(String entity, String entityKey) deleteFn,
  }) async {
    final rows = await _dao.pendingRows();
    for (final row in rows) {
      try {
        if (row.operation == 'delete') {
          await deleteFn(row.entity, row.entityKey);
        } else {
          await upsertFn(row.entity, row.entityKey, jsonDecode(row.payload) as Map<String, dynamic>);
        }
        await _dao.markSent(row.id);
      } catch (e) {
        await _dao.markFailed(row.id, e.toString());
        // Deliberately continue to the next row rather than abort the whole
        // drain — one failing entity must not block every other pending row.
      }
    }
  }
}
```
