<objective>
Give the offline outbox a consumer. Plan 21-03 built `SyncOutboxService.drain()` and plans
21-04/21-05 wired every repository to enqueue into the queue, but nothing in `lib/` ever
constructs the service or calls `drain()`. The queue is write-only in production: rows go in
and never come out.

This was found on a real device on 2026-08-04 (see `MANUAL-VERIFICATION-21.md`). First-login
migration works, because it calls `migrate_account_data` directly and bypasses the outbox
entirely — but every local change after that stays on the device forever. SYNC-05 ("changes
made while offline reach the cloud once a connection returns") is therefore not delivered.

Scope is deliberately narrow: wire the existing, already-tested `drain()` to a trigger. Do not
build a sync engine.
</objective>

<context>
**Why the full test suite is green despite this defect.** `drain()` has thorough unit tests
(`test/services/sync_outbox_service_test.dart`) and they all pass. The gap is not in the
function — it is that no production code calls it. Every test in this phase verified behaviour
*given* a call; none verified that a call site exists. That asymmetry is the actual lesson, and
it is why this plan's second task adds a wiring test rather than more `drain()` tests.

**How the work went missing.** Responsibility was deferred down the plan chain and then
dropped. `21-03` said wave 3 (`21-04`/`21-05`) would wire the real Supabase calls into
`drain()`'s callbacks. `21-04` said the drain step lands in `21-06`/`21-07`. Neither `21-06`
nor `21-07` mentions `drain` at all. No executor deviated from its plan; the plan set never
assigned this to anyone. Treat that as a planning-process finding, not an execution failure.

**Scope boundary, from REQUIREMENTS.md "Out of Scope".** No backoff schedules, no connectivity
listeners, no background/periodic draining. The trigger must therefore be foreground- and
event-driven only. `CloudSyncReconciler.reconcileOnForeground` is the existing, correct place —
it already runs on the app-foreground path wired up by plan 21-04, and draining there gives
SYNC-05 its "once a connection returns" behaviour without any new scheduling machinery.

**Also drain after a successful sign-in.** `AccountSyncService.onSignIn`'s
`pushLocalToCloud` branch calls `enqueueCurrentState()` on the repositories, which enqueues and
then leaves the rows sitting there. Without a drain on that path, the second sign-in leaves the
status text stuck on "Wordt gesynchroniseerd..." — exactly the observed symptom.

**Send closures.** `drain()` takes the send operation as injected callbacks precisely so this
file, not `sync_outbox_service.dart`, owns the `SupabaseClient`. Compose them from the existing
constants in `lib/data/remote/supabase_tables.dart` — never hardcode table names. Note the
per-entity difference established in 21-05: `planned_rides` deletes need the compound
`(user_id, ride_id)` filter parsed out of `entityKey`, while the two single-row domains key on
`user_id` alone.

**REG-05 trap.** `lib/data/database/sync_outbox_entity_types.dart` exists as a separate file
because the REG-05 structure test matches substrings on file paths, and a filename containing
"supabase" tripped it once already. Keep the Supabase-touching wiring in
`cloud_sync_reconciler_provider.dart` (a providers file, already excluded from the background
isolate's import graph) and do not move entity-type constants around.
</context>
