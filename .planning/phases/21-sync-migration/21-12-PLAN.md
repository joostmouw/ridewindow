<objective>
Make the outbox actually able to send. Plan 21-11 fixed the disposed-`Ref` bug and the drain now
runs — confirmed on device 2026-08-04 on build 1.0.16+17, where `adb logcat | grep -i disposed`
went from two hits to zero. But the account row still reads "Syncing..." forever, because the
availability payload is not a row.

`AvailabilityRepository` enqueues:

```dart
payload: jsonEncode(toRecurringRow(hours))   // → {"1-9":"work","6-14":"custom"}
```

and `CloudSyncReconciler.drainOutbox()`'s `upsertFn` does `client.from(table).upsert(payload)`.
So PostgREST is handed `"1-9"` and `"6-14"` as **column names** of `public.availability`, whose
actual columns are `user_id`, `recurring`, `version`, `updated_at`. That request cannot succeed —
not intermittently, not under any network condition. The row fails, `markFailed` bumps its attempt
count, and it is retried on every foreground for the rest of the device's life.

`profiles` and `planned_rides` are correct (`UserProfile.toRow`/`PlannedRide.toRow` both emit real
columns including `user_id`), which is why a profile change appears to sync while the pending count
never reaches zero.
</objective>

<context>
**How the shape got wrong, and why nothing caught it.** The first-login migration RPC nests the
same map correctly — `'p_availability_recurring': toRecurringRow(availabilityHours)` — and the read
path expects `row['recurring']` (`CloudReconcileService.parseAvailabilityRow`). Only the outbox
enqueue path skipped the wrapper. The unit test then froze the mistake in place:

```dart
// test/data/repositories/availability_repository_test.dart:152
expect(jsonDecode(pending.single.payload), equals(toRecurringRow(hours)));
```

That assertion is true of the buggy code and would be false of correct code. It is the third time
this phase that a test certified the shape of a thing rather than whether the thing works —
21-10 asserted a call site existed, 21-11 asserted a call reached its work, and this one asserted a
payload equalled a helper's output without ever asking whether that output was a legal row.

**Silence is the real defect.** `SyncOutboxService._drainInternal` catches per row and calls
`_dao.markFailed(row.id, e.toString())` with no logging at all. The error text lands in the
`lastError` column and is never surfaced anywhere — not in logcat, not in the UI, not in the hidden
debug menu. A payload that could never be accepted retried silently for hours and the only visible
evidence was a status string that would not change. Fixing the payload without fixing the silence
just moves the next bug's discovery cost onto the next device session.

**Wedged rows already exist.** Joost's device has at least one availability row enqueued in the
broken shape (the 2026-08-04 morning session set 120 hour blocks). After a payload fix that row is
still in the local queue, still in the old shape, and still unsendable. Shipping only the fix leaves
the device reading "Syncing..." forever, which looks exactly like the bug not being fixed.

**Scope boundary.** No backoff schedules, no connectivity listeners, no background draining
(REQUIREMENTS.md "Out of Scope", restated in 21-10 and 21-11). Dropping a permanently-failing row
is not a retry policy — it is refusing to retry something that provably cannot succeed.
</context>
