<objective>
Stop diagnosing blind. On 1.0.16+17 the disposed-Ref bug from 21-11 is provably gone
(`adb logcat | grep -i disposed` is empty after a foreground cycle, where the same grep on +16
returned two lines), but the account row still reads "Syncing..." — so `watchPendingCount()` is
still above zero and rows are still not getting sent.

We cannot see why, and that is a defect in its own right. `SyncOutboxService._drainInternal`
catches per row and calls `_dao.markFailed(row.id, e.toString())` **without logging anything**.
The error is written to Drift's `lastError` column, which no code path anywhere reads or
displays. Every failed send is therefore invisible.

This plan does not guess at the send failure. It makes the failure speak, and it puts
`lastError` where Joost can read it on the phone itself — no adb, no laptop.
</objective>

<context>
**Where the silence is.**

1. `SyncOutboxService._drainInternal` — `catch (e) { await _dao.markFailed(row.id, e.toString()); }`.
   No log. This is the main one.

2. `CloudSyncReconciler.drainOutbox`'s `upsertFn` — `final table = _tableForEntity(entity); if
   (table == null) return;`. Returning normally means the caller then runs `markSent(row.id)`,
   which **deletes the row**. An unrecognised entity string is silently discarded, not retried,
   not reported.

3. Same method's `deleteFn` — returns early for any entity other than `planned_ride`, and for an
   `entityKey` without a `:` separator. Both paths likewise end in `markSent`, i.e. a silent
   drop.

Cases 2 and 3 keep their current drop-rather-than-retry behaviour on purpose: a row that can
never be sent must not wedge the outbox forever, and the counter must be able to reach zero.
What changes is that they stop being silent.

**Why `lastError` also needs a UI.** Step 1 of the diagnosis in STATE.md (check
`profiles.notif_evening_before` in the Supabase dashboard) needs Joost. Everything here is
designed so the *next* device session answers the question on its own: open the debug menu, read
the actual error per row, optionally clear the outbox and watch whether the counter stays at
zero. That distinguishes "old poisoned rows from this morning" from "the drain still fails
completely" without a second round trip.

**Deliberately out of scope.** No retry/backoff policy, no dead-letter table, no attempt cap.
Those are real decisions about data loss and belong in their own plan, after we know what the
error actually says. This plan only removes the blindfold.
</context>
