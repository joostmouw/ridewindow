<objective>
Make deleting a planned ride actually stick. Found on device 2026-08-05 while verifying 21-13:
Joost deleted two rides through the app's own trash button and they came back on the next sync.

`reconcileOnForeground()` pulls before it pushes:

```
await _reconcileProfile(...)        // pull
await _reconcileAvailability(...)   // pull
await _reconcilePlannedRides(...)   // pull + union-merge, writes local
...
await drainOutbox();                // push — only now does the delete leave
```

So: `remove()` drops the ride locally and enqueues a `delete`. The next foreground reads the cloud,
which still holds the row because the delete has not been sent yet, and the union merge puts the
ride back into the local list. The drain then deletes the cloud row — but local already has it
again, so the following cycle reports it as `localOnly` and pushes it straight back up.

`mergePlannedRides` is a union and structurally cannot express a deletion; its own doc comment says
so ("without ever deleting a ride from either side as a side effect"). That is a reasonable design
**provided local intent is flushed first**. It is not, so the pull always beats a pending delete.

This is not limited to deletes: any local change sitting in the outbox is at risk of being
overwritten by a pull that runs before it is sent. Deletes are simply where it is total.
</objective>

<context>
**Why this survived 21-10 through 21-13.** Each of those plans fixed the drain itself — that it was
called, that it reached its work, that its payload was legal, that its key survived Postgres. All
four asked "does the push work?". None asked "does the push happen at the right moment relative to
the pull?". The ordering was never wrong in a way any single-component test could see, because both
components are individually correct.

**Push-then-pull is the standard outbox ordering** and the reason is exactly this case: the local
queue holds the user's *intent*, the cloud holds the last *agreed* state. Reading agreed state
before submitting intent discards the intent.

**Draining twice is deliberate, not belt-and-braces.** The reconcile's merge enqueues upserts for
local-only rides (`result.localOnly`). Those need a drain after the merge or they wait a whole
cycle. So the correct shape is drain → reconcile → drain. `SyncOutboxService.drain()` already has a
re-entrancy guard (plan 21-10) and a drain over an empty queue is a logged no-op, so the second
call is cheap and safe.

**Testability is the real finding.** `CloudSyncReconciler` reaches for `Supabase.instance.client`
directly, so the order of its network calls cannot be observed from a test without a live Supabase.
That is why an ordering defect could ship. This plan adds a source-order assertion — weak, and the
weakness is the point — and records making those dependencies injectable as the structural remedy,
which is out of scope here.
</context>
