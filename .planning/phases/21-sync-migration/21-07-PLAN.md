<objective>
Wire plan 21-06's `AccountSyncService` into the one place ARCHITECTURE.md §4 names as its trigger: the account section's sign-in flow. This is where MIG-01/02/03 stop being tested-in-isolation logic and become something a real sign-in actually does — and where D-04/D-05's two-button conflict dialogs and D-06/D-07's sync status text finally exist.

**The ordering hazard this plan must get right:** `account_section.dart` already has a Phase 19 flow, `_checkAccountSwitch()`, that reads `account.lastSyncedUid`, resolves `firstSignIn`/`sameAccount`/`differentAccount` via the (untouched, do-not-modify) local-only `resolveAccountSwitch()`, shows its own keep-or-wipe dialog for a genuine account switch, and **writes the new uid back to `account.lastSyncedUid`** in every branch. Plan 21-06's `AccountSyncService.onSignIn()` needs the value that key held **before** that write — otherwise `resolveAccountSync`'s MIG-02 branch (different account) becomes unreachable, because by the time it looks, Phase 19's own flow has already normalized the key to match the new uid. `_checkAccountSwitch()` already captures that original value into a local variable (`lastSyncedUid`, read once near the top, before either branch's `prefs.setString` call) — this plan reuses that exact local variable rather than re-reading the key a second time.

**Why this composes onto `_checkAccountSwitch()` rather than a new call site:** appending the `AccountSyncService.onSignIn()` call to the *end* of `_checkAccountSwitch()` (after both its branches have finished) means it automatically fires from both places that method is already called from today — the interactive sign-in flow (`_handleSignInSuccess`) and the reactive cold-start path (`build()`'s `ref.listen(authStateProvider, ...)`, which handles a restored session) — and it automatically reuses the existing `_lastCheckedUid` dedup guard, so this plan needs zero new guard logic.

**Sequencing is also a correctness requirement, not a style choice:** a genuine account switch's keep-or-wipe decision (Phase 19) must be fully resolved — local storage settled — before `AccountSyncService` looks at it, or a "start fresh" wipe could race a cloud push of the *previous* account's leftover local data into the *new* account's cloud row. `_checkAccountSwitch()` already awaits the wipe before either `prefs.setString` call; appending `onSignIn()` after that point (not before) is what keeps this safe.

Output: `account_section.dart` calling `AccountSyncService.onSignIn()` correctly ordered and correctly sourced, up to two sequential conflict dialogs, and the sync-status text.

**`_checkAccountSwitch()`'s current shape (read the real file before editing — this is a close paraphrase of its structure, not a literal diff):**

```dart
Future<void> _checkAccountSwitch(String signedInUid) async {
  if (_lastCheckedUid == signedInUid) return;
  _lastCheckedUid = signedInUid;

  final prefs = await SharedPreferences.getInstance();
  final lastSyncedUid = prefs.getString(_kLastSyncedUidKey); // <- the pre-write snapshot to reuse
  final decision = resolveAccountSwitch(signedInUid: signedInUid, lastSyncedUid: lastSyncedUid);

  switch (decision) {
    case AccountSwitchDecision.firstSignIn:
    case AccountSwitchDecision.sameAccount:
      await prefs.setString(_kLastSyncedUidKey, signedInUid);
      break;
    case AccountSwitchDecision.differentAccount:
      // ... existing dialog + optional wipe ...
      await prefs.setString(_kLastSyncedUidKey, signedInUid);
      break;
  }

  // NEW: append here, after both branches have settled local storage.
  await _runAccountSync(signedInUid, lastSyncedUid);
}
```

**`_runAccountSync()` — the new method this plan adds, owning D-04/D-05's sequential dialogs:**

```dart
Future<void> _runAccountSync(String userId, String? preSwitchLastSyncedUid) async {
  final service = AccountSyncService(/* construct with Supabase.instance.client, the app database's syncOutboxDao, the three repositories (obtained via ref.read(...RepositoryProvider.future)), a CloudReconcileService, and a migrateFn closure wrapping client.rpc(kMigrateAccountDataRpc, params: p) */);

  final prompts = await service.onSignIn(userId, lastSyncedUid: preSwitchLastSyncedUid);

  for (final prompt in prompts) {
    if (!mounted) return;
    final s = S.of(context);
    final isProfile = prompt.domain == SyncDomain.profile;
    final keepLocal = await showDialog<bool>(
      context: context,
      barrierDismissible: false,
      builder: (ctx) => AlertDialog(
        title: Text(isProfile ? s.accountConflictProfileTitle : s.accountConflictAvailabilityTitle),
        content: Text(isProfile ? s.accountConflictProfileBody : s.accountConflictAvailabilityBody),
        actions: [
          TextButton(onPressed: () => Navigator.of(ctx).pop(true), child: Text(s.accountConflictKeepLocalAction)),
          TextButton(onPressed: () => Navigator.of(ctx).pop(false), child: Text(s.accountConflictKeepCloudAction)),
        ],
      ),
    );
    await service.resolvePrompt(prompt, userId, keepLocal: keepLocal ?? true);
  }

  if (prompts.isNotEmpty) {
    await service.markSynced(userId);
  }

  if (mounted) {
    ref.invalidate(profileProvider);
    ref.invalidate(availabilityProvider);
  }
}
```

The `for` loop's `await` inside each iteration is what makes the two dialogs sequential (D-05) — do not use `Future.wait`/parallel dialog presentation. `prompts` is ordered `[profile, availability]` when both are present, per plan 21-06's `onSignIn()` evaluation order — so no additional sorting is needed here.
