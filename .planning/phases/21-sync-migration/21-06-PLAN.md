<objective>
Build `AccountSyncService`, the orchestrator ARCHITECTURE.md §5 describes as "the ONE place migration/conflict logic lives" — it wires plan 21-01's pure `resolveAccountSync()` to the real infrastructure (plan 21-02's schema/RPCs, plans 21-03/21-04/21-05's outbox and repositories), per ARCHITECTURE.md §7 step 6.

This plan builds the **service only, no UI**. The two-button conflict `AlertDialog` (D-04/D-05) is plan 21-07's job — this plan's `onSignIn()` resolves everything it can resolve on its own (push/pull/noop) and returns a small list of "this domain needs a human decision" prompts for anything it can't. Keeping the boundary here means this service is fully unit-testable without pumping any widget.

**MIG-05/06's atomicity is earned by a trigger condition, not by every push:** the `migrate_account_data` RPC (plan 21-02) is the all-or-nothing, server-acknowledged transaction — but it is only correct to call it for a genuine *first login* (neither `profiles` nor `availability` has a cloud row yet for this user). An ordinary later divergence that resolves to "push local" is just a normal write through the existing per-domain outbox (plan 21-04) — there is no three-table atomicity requirement for that case, since it isn't populating a brand-new account from scratch. This plan is precise about that distinction; do not call the RPC on every push.

Purpose: make MIG-01/02/03 real, MIG-05/06/07 verifiably true, and give MIG-08 an exact, automatable target to assert against.

Output: `migration_payload.dart` (the pure RPC-payload builder — this is what MIG-08 tests against), `AccountSyncService` (the orchestrator plan 21-07 calls from the sign-in UI).

  return {

    'p_allowed_durations': profile.allowedDurations,

    'p_location_override': profile.locationOverride,
    'p_user_name': profile.userName,
    'p_notif_evening_before': profile.notifEveningBefore,
    'p_notif_morning_of': profile.notifMorningOf,
    'p_notif_weekly_digest': profile.notifWeeklyDigest,
    'p_availability_recurring': toRecurringRow(availabilityHours), // from availability_key.dart, plan 21-04

Note the `p_planned_rides` entries deliberately omit `user_id` (each element is `{rideId, startAt, endAt, plannedScore}` only) — the SQL function's loop body only reads `ride->>'rideId'`/`'startAt'`/`'endAt'`/`'plannedScore'` from each array element (plan 21-02's `migrate_account_data` body) and derives `user_id` once, for the whole call, from `auth.uid()`. Use `PlannedRide.toRow(userId)`'s existing key names (`rideId`... wait — `PlannedRide.toRow()` from plan 21-05 produces snake_case keys (`ride_id`, `start_at`, `end_at`, `planned_score`) matching the Postgres column names directly, since that same map is also used for direct per-ride outbox upserts. Re-check plan 21-02's SQL loop body: it reads `ride->>'rideId'`, `ride->>'startAt'`, `ride->>'endAt'`, `ride->>'plannedScore'` (camelCase) from each JSONB array element — **this is a deliberate difference from the column names**, because the array elements are a client-constructed JSON payload for one specific RPC call, not a direct table row. Build each planned-ride array element as `{'rideId': r.rideId, 'startAt': r.start.toIso8601String(), 'endAt': r.end.toIso8601String(), 'plannedScore': r.plannedScore}` (camelCase, matching plan 21-02's SQL exactly) rather than reusing `toRow()`'s snake_case shape — these are two different payload shapes for two different call sites, and MIG-08's test must assert this exact camelCase shape for the RPC array, not the snake_case row shape.

**`AccountSyncService` — public surface, no UI:**

```dart
enum SyncDomain { profile, availability }

class PendingSyncPrompt {
  const PendingSyncPrompt(this.domain);
  final SyncDomain domain;
}

class AccountSyncService {
  AccountSyncService({
    required this.outbox,
    required this.profileRepo,
    required this.availabilityRepo,
    required this.plannedRidesRepo,
    required this.cloudReconcile, // plan 21-04's CloudReconcileService
    required this.migrateFn, // Future<void> Function(Map<String,dynamic> params) — wraps client.rpc(kMigrateAccountDataRpc, params: ...)
    required this.writeLastSyncedUid, // Future<void> Function(String userId)
  });

  // ... fields ...

  /// Called once, right after sign-in succeeds. [lastSyncedUid] MUST be the
  /// value read from `account.lastSyncedUid` BEFORE the caller's own
  /// account-switch handling (the existing Phase 19 flow in
  /// account_section.dart) had a chance to overwrite it for this sign-in —
  /// that flow already persists the new uid to the same key as part of its
  /// own firstSignIn/sameAccount/differentAccount resolution, and it MUST
  /// run before this method (a genuine account switch has to resolve
  /// keep-or-wipe before this method can trust local storage at all — see
  /// plan 21-07's ordering requirement). If this method re-read the key
  /// itself at call time, it would always see the value the switch flow
  /// just wrote (== userId), making resolveAccountSync's MIG-02 branch
  /// unreachable. Callers must capture the snapshot first and pass it in.
  ///
  /// Resolves profile and availability independently. Applies every
  /// non-prompt decision immediately. Returns the (possibly empty) list of
  /// domains that need a user choice. If the list is empty,
  /// account.lastSyncedUid is already (re-)written by the time this returns.
  Future<List<PendingSyncPrompt>> onSignIn(String userId, {required String? lastSyncedUid}) async {
    final profileMeta = await cloudReconcile.readCloudProfile(userId); // null = no cloud row
    final availabilityMeta = await cloudReconcile.readCloudAvailability(userId);

    // MIG-05/06: genuine first login for THIS account — neither domain has
    // a cloud row yet. One atomic RPC populates all three tables from
    // current local state, rather than three independent per-domain pushes.
    if (profileMeta == null && availabilityMeta == null) {
      final profile = profileRepo.readLocal(/* systemLanguageCode from caller, see action notes */);
      final hours = availabilityRepo.readLocal();
      final rides = plannedRidesRepo.readLocal();
      await migrateFn(buildMigrationRpcParams(profile: profile, availabilityHours: hours, plannedRides: rides));
      await writeLastSyncedUid(userId);
      return const [];
    }

    final prompts = <PendingSyncPrompt>[];

    final profileDecision = resolveAccountSync(
      userId: userId,
      lastSyncedUid: lastSyncedUid,
      cloudRowExists: profileMeta != null,
      cloudUpdatedAt: profileMeta?.updatedAt,
      localUpdatedAt: _localDateTime(profileRepo.readUpdatedAt()),
    );
    if (profileDecision == SyncDecision.promptUser) {
      prompts.add(const PendingSyncPrompt(SyncDomain.profile));
    } else {
      await _applyProfileDecision(profileDecision, userId, profileMeta);
    }

    final availabilityDecision = resolveAccountSync(
      userId: userId,
      lastSyncedUid: lastSyncedUid,
      cloudRowExists: availabilityMeta != null,
      cloudUpdatedAt: availabilityMeta?.updatedAt,
      localUpdatedAt: _localDateTime(availabilityRepo.readUpdatedAt()),
    );
    if (availabilityDecision == SyncDecision.promptUser) {
      prompts.add(const PendingSyncPrompt(SyncDomain.availability));
    } else {
      await _applyAvailabilityDecision(availabilityDecision, userId, availabilityMeta);
    }

    if (prompts.isEmpty) {
      await writeLastSyncedUid(userId);
    }
    return prompts;
  }

  /// Called by the UI (plan 21-07) after the user picks a side for a
  /// prompted domain. [keepLocal] true = pushLocalToCloud, false =
  /// pullCloudToLocal — there is no third choice at this point, the
  /// ambiguity that caused the prompt is resolved by the user's pick.
  Future<void> resolvePrompt(PendingSyncPrompt prompt, String userId, {required bool keepLocal}) async {
    final decision = keepLocal ? SyncDecision.pushLocalToCloud : SyncDecision.pullCloudToLocal;
    switch (prompt.domain) {
      case SyncDomain.profile:
        final meta = await cloudReconcile.readCloudProfile(userId);
        await _applyProfileDecision(decision, userId, meta);
      case SyncDomain.availability:
        final meta = await cloudReconcile.readCloudAvailability(userId);
        await _applyAvailabilityDecision(decision, userId, meta);
    }
  }

  /// Called by the UI once every prompt from a given onSignIn() call has
  /// been resolved via resolvePrompt(). Not called by onSignIn() itself
  /// when prompts is non-empty — the UI owns sequencing D-05's two dialogs.
  Future<void> markSynced(String userId) => writeLastSyncedUid(userId);

  // _applyProfileDecision/_applyAvailabilityDecision: pushLocalToCloud ->
  // profileRepo/availabilityRepo.save() again with stamp:false is wrong —
  // pushing means the LOCAL data is already correct and just needs to reach
  // the cloud, so re-save with stamp:true is also wrong (it would move the
  // local timestamp further ahead of what's about to be pushed for no
  // reason). Instead call the repository's outbox-enqueue path directly —
  // add a small `enqueueCurrentState()` method to ProfileRepository/
  // AvailabilityRepository (same shape as PlannedRidesRepository's
  // enqueueUpsert() from plan 21-05) that enqueues the *current* local data
  // without rewriting local storage or its timestamp. pullCloudToLocal ->
  // read the full cloud row (cloudReconcile.readCloudProfile/Availability
  // already returns the parsed profile/hours alongside updatedAt from plan
  // 21-04) and call repo.save(cloudData, stamp: false) followed by
  // repo.stampUpdatedAt(cloudUpdatedAt) — MIG-07: this overwrites field
  // values, it never removes/clears a SharedPreferences key. noop -> do
  // nothing.
}
```
