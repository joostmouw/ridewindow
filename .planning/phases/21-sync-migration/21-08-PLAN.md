<objective>
Ship AUTH-09's actual UI: a "Delete account" action in the signed-in row of the account section, per D-01/D-02/D-03 (21-CONTEXT.md). This is the last piece that makes the schema-level `on delete cascade` (plan 21-02) something a real user can actually trigger and see confirmed.

**D-01, exactly:** a single `AlertDialog` — same visual pattern as the existing account-switch dialog at `account_section.dart` (Cancel/confirm, `barrierDismissible: false`) — with explicit "this cannot be undone" warning text. No type-to-confirm text field, no re-authentication step. This is a deliberate, user-approved scope limit (21-CONTEXT.md's `<deferred>` section: both omissions were "considered and explicitly declined for this milestone, not deferred as future work items").

**D-02, exactly:** on confirmed deletion, call the RPC, then sign out (same effect as the existing sign-out path), then show a short snackbar ("Account verwijderd" / "Account deleted"). No dedicated confirmation screen — the user lands on the normal signed-out row.

**D-03, exactly and non-negotiably:** deletion never touches local on-device data. The app must keep working fully locally after this, exactly like an ordinary sign-out (AUTH-03's existing guarantee) — the only difference from ordinary sign-out is that the *server* rows are also gone. Do not call `resetToDefaults()`/`clearAll()`/anything from the existing "start fresh" account-switch branch — that branch exists for a *different* reason (a new account arriving on the device) and reusing it here would be a D-03 violation, not a convenience.

**Why AUTH-09 needs its own real device+dashboard verification, not just a unit test:** `on delete cascade` is a schema promise, and plan 21-02's SQL migration/RLS deny test already proved the schema is live — but "the client can trigger it and the rows really vanish" is an end-to-end claim across auth, RPC, and cascading deletes that a `flutter test` run cannot fully prove without a live Supabase call. This plan's checkpoint task is that proof.

Output: the delete-account button, dialog, RPC call, sign-out, snackbar, l10n, unit/widget tests, and a real deployed-project verification.

```dart
Future<void> _confirmAndDeleteAccount(BuildContext context) async {
  final s = S.of(context);
  final confirmed = await showDialog<bool>(
    context: context,
    barrierDismissible: false,
    builder: (ctx) => AlertDialog(
      title: Text(s.accountDeleteConfirmTitle),
      content: Text(s.accountDeleteConfirmBody), // must state, plainly, that this cannot be undone
      actions: [
        TextButton(onPressed: () => Navigator.of(ctx).pop(false), child: Text(s.cancel)),
        TextButton(
          onPressed: () => Navigator.of(ctx).pop(true),
          style: TextButton.styleFrom(foregroundColor: Theme.of(ctx).colorScheme.error),
          child: Text(s.accountDeleteConfirmAction),
        ),
      ],
    ),
  );

  if (confirmed != true) return;

  try {
    await Supabase.instance.client.rpc(kDeleteOwnAccountRpc);
    await Supabase.instance.client.auth.signOut();
    if (!mounted) return;
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text(s.accountDeletedSnackbar)),
    );
  } catch (e) {
    debugPrint('AccountSection: delete_own_account mislukt: $e');
    if (!mounted) return;
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text(s.accountDeleteError)),
    );
    // Deliberately does NOT sign out on failure — a failed server-side
    // deletion must not present as a successful one (D-02's ordering:
    // sign-out only follows a confirmed successful RPC call).
  }
}
```
