<objective>
Wire the web-only prerequisites for Google Calendar OAuth to survive Safari's synchronous-user-gesture popup requirement (CAL-06), and prove on a local Chrome dev server that the existing scope-only `authorizeScopes()` flow actually opens a popup and creates a real Calendar event on web at all -- the single most important unresolved unknown from RESEARCH.md (Open Question 1 / Assumption A1).

**Framing note (MVP_MODE):** ROADMAP.md's Phase 15 `**Goal**:` line is written as a technical/UX outcome ("Web users can add a ride slot to Google Calendar directly from the deployed app, with sign-in surviving Safari's popup blocker and FedCM incompatibility"), not in strict `As a / I want to / so that` format -- consistent with every other v2.0 phase goal in this ROADMAP (Phases 11-14 precedent, all planned the same way). Reframed for reference: **As a** web user who found a good ride window, **I want to** tap one button and have it land on my real Google Calendar without a confusing sign-in dance, **so that** I actually book the ride instead of forgetting about it. Per the orchestrator's instruction this plan is one vertical slice: Task 1 obtains the one external credential this slice needs, Task 2 wires the code, Task 3 proves the whole flow works end-to-end for a real user in a real browser (dev domain). Plan 15-02 extends the same slice to the real deployed production domain and real iPhone Safari (CAL-07), which is out of this plan's scope only because no Firebase Hosting deployment exists yet (dependency conflict, not a difficulty judgment).

**Pre-existing-code audit (done during planning, do not re-discover this):**
- `lib/services/calendar_service.dart` (Phase 9) never calls `GoogleSignIn.instance.authenticate()` -- it goes straight to `GoogleSignIn.instance.authorizationClient.authorizeScopes([CalendarApi.calendarEventsScope])` on the bare singleton. This means FedCM (which only governs `authenticate()`/One Tap) is very unlikely to be the actual constraint for this feature (RESEARCH.md Pitfall 2) -- do not build any FedCM-specific code in this plan.
- `CalendarService._ensureInitialized()` currently does `if (_initialized) return; await GoogleSignIn.instance.initialize(); _initialized = true;` and is called from `addRideSlotToCalendar()` right before the popup-opening `authorizeScopes()` call. On the *first* tap of a session this `await` is a real async gap before the popup call -- exactly the pattern Safari's popup blocker rejects (RESEARCH.md Pitfall 1). This plan does not remove `_ensureInitialized()` (native still needs its lazy behavior per CAL-02) -- it adds a *second*, web-only, eager entry point that makes `_ensureInitialized()` a no-op by the time the user taps.
- `lib/main.dart` already has one `kIsWeb`-gated inverse-guard precedent to copy exactly: `if (!kIsWeb) { await Workmanager().initialize(...); ... }` at lines 55-67, placed *after* `runApp()` so it never blocks the first frame. `main.dart` imports `kIsWeb` directly (not `isWebPlatform`) because `main()` itself has no `flutter test` coverage -- this is the one established exception to the `isWebPlatform` convention (confirmed in 15-PATTERNS.md); keep using raw `kIsWeb` here for consistency with the rest of this file.
- `web/index.html` currently has no `google-signin-client_id` (or any OAuth-related) meta tag -- this is genuinely the first of its kind in this repo (15-PATTERNS.md: "No Analog Found").
- No new pubspec dependencies are needed. `google_sign_in` 7.2.0, `google_sign_in_web` 1.1.3 (transitive), `extension_google_sign_in_as_googleapis_auth` 3.0.0, `googleapis` 16.0.0 are already pinned and already used by the Android flow (RESEARCH.md Standard Stack).

Purpose: De-risk the single biggest unknown (does the existing Android-shaped OAuth pattern even open a popup on web?) before any production deployment work happens, and fix the one real, already-diagnosed Safari-breaking bug (the async gap) at the source.
Output: `CalendarService.warmUpForWeb()`, a web-only eager-init call in `main.dart`, a real Web OAuth client ID wired into `web/index.html`, matching tests, and a manually-verified real Chrome popup-to-Calendar-event flow on `localhost:5000`.
</objective>
